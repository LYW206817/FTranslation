## 1. 背景与目标

### 1.1 现状

v44 已经完成「存」这一环：结果卡第 4 个按钮「保存」→ `NoteClassifier.Classify` 判类型 → `POST /api/v1/notes` → `notes` 单表（`kind` 区分单词/短语/语句）。`NotesWindow` 三栏（左 150 三个本 / 中列表 / 右 300 详情）。

但有两个断开的地方：

1. **截图翻译出来的东西存不进单词本**。`src/FastTranslation.Core/ImageTranslationTypes.cs:10-17` 的 `ImageTranslationResult` 只有译后 JPG 字节和 OSS 临时 URL，**没有任何文本**；`QwenMtImageTranslator.BuildPayload` 只发 `image_url` + 语言，`TryReadImageUrl` 只解 `output.image_url`。于是 `ImageResultWindow.cs:36-41` 那三个按钮只有「复制图片 / 另存为… / 关闭」。
2. **存下来的东西没有回头路**。`reviews` 表只在规格里预留（`2026-10-28-account-and-billing-design.md:149`，注释「阶段3才写」），代码里不存在；`notes` 表也没有任何记忆状态字段。用户存完就再也见不到。

### 1.2 用户原话（需求来源）

> 「给截图翻译的内容保存到单词本，用户可以进行记录之后可以学习，比如，用户可以在单词本里记住/熟悉/模糊/忘记等，进行分类」

拆成三件事：**截图 → 存 → 按四档记忆程度学习**。这三件事共同构成产品差异点：竞品调研（见 §13）显示，Windows 系统级「截图 → 存 → 按记忆程度复习」的闭环目前无人做——欧路/有道有复习但截图要绕路，开源划词工具（Easydict/Pot/STranslate）有截图但生词本只是收藏夹。

### 1.3 目标

- 截图翻译的结果能在结果窗里一键存进单词本，且用户能当场看见 OCR 识别得对不对。
- 每条笔记能被标成 忘记 / 模糊 / 熟悉 / 记住 四档之一，并据此算出下次该复习的时间。
- 有一个地方能一口气把「今天该复习的」过完，不用在列表里翻。
- 不引入新依赖、不引入新框架（项目约定），算法是一个纯函数 + 几个整数列。

### 1.4 非目标

- 不做完整 FSRS / SM-2 调度，不建复习事件表（见 §3 D2、§5.4）。
- 不存截图原图或译图。
- 不做导出 CSV / Anki（将来要导出再加，数据已经够）。
- 不做通知、打卡、连续天数、排行榜。
- 不改现有划词翻译链路、不改现有保存按钮的行为。

## 3. 关键决策记录

每一条都来自与用户的一问一答，此处只记结论与理由；理由里带「因为」的部分是后面不能再推翻的依据。

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| D1 | OCR 时机 | **选完框立刻做**，与图片翻译并行 | 结果窗能显示「识别到的原文」，用户当场能看见识别对不对、能改。代价是每次截图多一次 OCR 调用（约 1 分钱）和一次往返 |
| D2 | 四档深度 | **标签 + 算下次复习日期**，不做完整 FSRS | 用户要的是「分类 + 之后能学」，不是算法研究。整数列 + 一个纯函数就够，实现风险低 |
| D3 | 复习界面位置 | **独立窗口** `ReviewWindow` | 复习是专注时段，需要大字号卡片、遮罩揭示和键盘流；塞进主窗口会被侧栏和标题抢走纵深感。主窗口里它是一个侧栏入口（红点角标显示今日到期数），点开才开窗 |
| D4 | 图片存储 | **只存文本**，不存原图/译图 | 复习自测靠「遮译文」，图用不上；存图要处理存储配额和隐私，收益为零 |
| D5 | 适用条目范围 | **所有条目都能标四档**，不限来源 | 划词存的、截图存的，走的都是 `notes` 表同一批行，没有理由区别对待 |
| D6 | 截图粒度 | **一张截图 = 一条笔记** | 多行文本经 `NoteClassifier` 会落到「语句」本（长度 > 80 或含句末标点）。切分成分句是下一版的事 |
| D7 | OCR 计费通道 | **跟随现有图片翻译链路**：登录走网关额度，未登录用自己 Key | 与 D1 一致即可，不新增一套计费心智 |
| D8 | 新条目入队 | **新条目也排进今日队列，每天限 20 条** | 像 Anki 的新词配额。不然存进去的东西永远不回头看，功能等于没有 |
| D9 | 四档间隔 | **10 分钟 / 1 天 / 3 天 / 7 天，连对翻倍** | 见 §5 |
| D10 | 降档语义 | **回退一档，不归零** | 一条背了 56 天的词点「忘记」，不该被打回新词堆；归零会让用户觉得前面的努力白费 |
| D11 | 自测方向 | **先看原文，想译文，再揭开** | 卡上只给原文，译文默认遮住，点「看答案」才揭开。防止「译文就在旁边扫一眼就当会了」 |
| D12 | 详情页标注 | **详情页也能直接标四档** | 接受「存完立刻定档、跳过自测」的代价，给用户一条快路径 |
| D13 | 主窗口形态 | **单窗口 + 左侧栏**，七页：首页 / 单词 / 短语 / 语句 / 复习 / 套餐 / 设置 | v2 效果图用户定稿（m00917「认可」）。原来四个独立窗口（`MainWindow` / `NotesWindow` / `AccountWindow` / `SettingsWindow`）合成一扇窗，只有复习窗新开。侧栏把入口从散落的 footer 按钮收拢成固定位置，用户不用记「哪个功能在哪个窗」 |
| D14 | 设置与套餐的宿主 | **搬进主窗口当页**，不再弹窗 | 同 D13。`SettingsWindow` 的 500px 独立窗在一扇 1040px 窗口里横向宽敞很多；`ShowDialog()` 的模态语义也被「保存/取消」固定条替代 |
| D15 | 复习窗的打开方式 | 侧栏「复习」项点击 → `ShowReview()` 单例 | 与现有 `ShowNotes()` 同构（`Windows.OfType<>().FirstOrDefault()`）。复习窗不嵌进主窗口，因为它需要独占焦点与键盘 |

## 4. 数据模型

### 4.1 `notes` 表新增列

沿用 `ServerDatabase.EnsureColumn`（`server/FastTranslation.Server/Storage/ServerDatabase.cs:62-86`，先 `PRAGMA table_info` 探测再 `ALTER TABLE ADD COLUMN`，幂等）：

```sql
ALTER TABLE notes ADD COLUMN stage       INTEGER NOT NULL DEFAULT 0;
ALTER TABLE notes ADD COLUMN due_at      INTEGER NOT NULL DEFAULT 0;
ALTER TABLE notes ADD COLUMN last_grade  TEXT    NOT NULL DEFAULT '';
ALTER TABLE notes ADD COLUMN review_count INTEGER NOT NULL DEFAULT 0;
ALTER TABLE notes ADD COLUMN lapses      INTEGER NOT NULL DEFAULT 0;
ALTER TABLE notes ADD COLUMN reviewed_at INTEGER NOT NULL DEFAULT 0;
```

| 列 | 语义 |
|---|---|
| `stage` | 间隔阶梯索引，0 = 从没评过（新词），1~7 见 §5.1 |
| `due_at` | 下次该复习的 unix 秒；`stage = 0` 时恒为 0（不看 due，看配额） |
| `last_grade` | 最近一次评分 `forgot` / `fuzzy` / `familiar` / `known`；空串 = 没评过 |
| `review_count` | 评过多少次，只增不减 |
| `lapses` | 点过多少次「忘记」，只增不减 |
| `reviewed_at` | 最近一次评分时间 |

`CREATE INDEX ix_notes_user_due ON notes(user_id, due_at) WHERE deleted_at IS NULL` —— 队列查询只走这一个索引。

**为什么不建 `reviews` 表**：现在的需求是「当前状态 + 下次时间」，事件流只是将来做统计/曲线才需要。`review_count` / `lapses` 两个计数器已经覆盖「这词我错了几次」这个用户真会看的维度。等真要做遗忘曲线再加表，那时也已有 `reviewed_at` 可作迁移起点。规格 §4.3 的 `reviews` 草案因此作废。

### 4.2 `NoteRecord` / `Note` / `NoteDto` 同步扩展

三处都要加，**都作为带默认值的尾参数**，这样现有构造点与调用点不用改：

- `server/FastTranslation.Server/Storage/NoteStore.cs` 的 `NoteRecord`
- `src/FastTranslation.Core/Notes/NoteTypes.cs` 的 `Note`
- `server/FastTranslation.Server/Api/Contracts.cs` 的 `NoteDto`

新增字段：`int Stage, long DueAt, string LastGrade, int ReviewCount, int Lapses, long ReviewedAt`。

客户端 `Note` 另加两个派生属性（不参与 wire）：

- `string GradeDisplay` → 「忘记 / 模糊 / 熟悉 / 记住 / 未评」
- `string DueLine` → 「10 分钟后」「3 天后」「今天到期」等，用于列表第三行与详情页

## 5. 调度算法：`ReviewSchedule`

### 5.1 间隔阶梯

`stage` 直接就是阶梯索引：

| stage | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 间隔 | —（未排期） | 10 分钟 | 1 天 | 3 天 | 7 天 | 14 天 | 28 天 | 56 天 |
| 秒 | 0 | 600 | 86 400 | 259 200 | 604 800 | 1 209 600 | 2 419 200 | 4 838 400 |

### 5.2 转移规则

```
记住 known     → stage >= 4 ? min(7, stage + 1) : 4
熟悉 familiar  → 3
模糊 fuzzy     → 2
忘记 forgot    → 1，且 lapses += 1
```

- 首次「记住」落在 7 天（stage 4），不是 10 分钟 —— 用户已经会了，没必要当天再见。
- 连续「记住」每次升一档：7 → 14 → 28 → 56，封顶 56 天。
- 降档**只改 stage 到目标值**：一条 stage 7 的词点「忘记」落到 stage 1（10 分钟后再来），不是 stage 0。`stage = 0` 永远只属于「从未评过分的新词」。这是 D10「回退一档不归零」的落实方式——按当前档位往下取一档，但地板是 1。

### 5.3 接口

新文件 `src/FastTranslation.Core/Notes/ReviewSchedule.cs`：

```csharp
public enum ReviewGrade { Forgot = 0, Fuzzy = 1, Familiar = 2, Known = 3 }

public static class ReviewSchedule
{
    public const int MaxStage = 7;

    /// <summary>Seconds to wait after a grade, per resulting stage. Index 0 is the unscheduled state.</summary>
    public static readonly IReadOnlyList<long> IntervalsSeconds = new long[]
    {
        0L, 600L, 86_400L, 259_200L, 604_800L, 1_209_600L, 2_419_200L, 4_838_400L,
    };

    public static int NextStage(int stage, ReviewGrade grade);

    /// <summary>Returns the new stage and the absolute due time (unix seconds). grade=null means "schedule as new".</summary>
    public static (int Stage, long DueAt) Schedule(int currentStage, ReviewGrade grade, long nowUnix);

    public static bool TryParseGrade(string? wire, out ReviewGrade grade);
    public static string ToWire(ReviewGrade grade);   // "forgot" / "fuzzy" / "familiar" / "known"
}
```

纯函数、零依赖、零 IO、不读时钟（`nowUnix` 由调用方传）。这是本次唯一真正「新写」的算法，也是单测的重点。

### 5.4 关于「一天」的定义

服务端所有时间戳是 UTC unix 秒（`ServerDatabase.NowUnix`）。但「今日」的边界必须是**用户本地零点**，否则北京用户早上 8 点前存的新词会被算到前一天。

因此：`dayStart`（用户本地零点的 unix 秒）**由客户端算好传给服务端**，服务端不猜时区。这是 D8 配额能对的前提。

## 6. 服务端 API

两个新端点，都挂在现有 `/api/v1/notes` group 内（`NotesEndpoints.cs`），因此自动继承 `RequireAuthorization()` 与 `Entitlement.AllowsNotebook` 这道唯一的付费闸门（订阅校验先于一切读写）。

### 6.1 `GET /api/v1/notes/review`

查询参数：`dayStart`（必填，unix 秒）、`newLimit`（默认 20，夹到 0..100）、`limit`（默认 50，夹到 1..200）。

返回：

```json
{
  "due":   [ NoteDto, ... ],   // 已到期：stage >= 1 AND due_at <= now，按 due_at ASC
  "fresh": [ NoteDto, ... ],   // 新词：stage = 0，按 created_at ASC，条数受配额限制
  "dueTotal":  37,             // 到期总数（不受 limit 截断，用于左栏角标）
  "freshQuota": 20,            // 今天还能放几张新词
  "limit": 50,
  "newLimit": 20
}
```

新词配额算法：`今天已入队的新词数 = COUNT(stage = 0 AND created_at >= dayStart)`，`freshQuota = max(0, newLimit - 已入队数)`。

**为什么用「今天存的新词数」而不是另建一张每日队列表**：新词的定义天然是 `stage = 0`，它一旦被评过就离开这个集合，计数自动收敛。不需要额外的状态机，也不会出现「队列表与 notes 表不同步」这种经典 bug。

响应类型新增 `ReviewQueueResponse(IReadOnlyList<NoteDto> Due, IReadOnlyList<NoteDto> Fresh, int DueTotal, int FreshQuota, int Limit, int NewLimit)`。

### 6.2 `POST /api/v1/notes/{id}/review`

请求体 `{"grade":"forgot|fuzzy|familiar|known"}`（新增 `GradeNoteRequest(string? Grade)`）。

处理顺序：

1. 订阅闸门（group 级已有）。
2. `grade` 解析失败 → **400 `grade_invalid`**。
3. `store.FindById(userId, id)` 未命中 → **404 `note_missing`**（沿用现有错误码，不新增）。
4. `ReviewSchedule.Schedule(record.Stage, grade, now)`。
5. `store.SetReview(userId, id, stage, dueAt, gradeWire, reviewedAt)`，`review_count += 1`、`forgot` 时 `lapses += 1`。
6. 返回更新后的 `NoteDto`。

`SetReview` 更新 `updated_at`：记忆状态变了，跨设备同步应该带上。

### 6.3 `NoteStore` 新增方法

```csharp
public IReadOnlyList<NoteRecord> ListDue(Guid userId, long nowUnix, int limit);
public (IReadOnlyList<NoteRecord> Items, int Total) ListFresh(Guid userId, long dayStartUnix, int limit);
public int CountFreshSince(Guid userId, long dayStartUnix);

```

## 7. 截图链路改造

### 7.1 三段调用与并发

```
选完框（CapturedImage.PngBytes 已在内存，不用重截）
  ├─ A. 图片翻译  qwen-mt-image-2.0                      → 译图 JPG
  └─ B. OCR       qwen-vl-ocr  → 原文 ─→ 文本翻译 qwen-mt-flash → 译文
```

A 与 B **并行发起**（`Task.WhenAll` 式的两个 `Task`，各自 try/catch），任一失败不拖垮另一条：

- A 成功 B 失败 → 照旧出译图，识别文本框显示「这次没识别出来」并说明原因，保存按钮置灰。
- A 失败 B 成功 → 出文本结果窗（只有文本，无图），保存按钮可用。这是**比现在更好的降级**：今天图片翻译失败就什么都没有。
- 两条都失败 → 托盘气泡报错，行为同现在。

### 7.2 OCR 客户端

新文件 `src/FastTranslation.Providers.QwenMt/QwenOcrClient.cs`，照 `QwenMtImageTranslator` 的骨架（重试一次、分类状态码、`QuotaRefusal.Describe`）。

- 端点：`POST https://dashscope.aliyuncs.com/api/v1/services/aigc/multimodal-generation/generation`
- 模型：`qwen-vl-ocr`
- 请求体：`input.messages[0].content = [{ "image": "data:image/png;base64,..." }]`
- **不传 prompt**：DashScope 对此模型的默认 prompt 就是「只输出图片中的文字内容，不要任何额外描述或格式」，正好是要的纯文本。
- 响应取 `output.choices[0].message.content[0].text`。

新文件 `src/FastTranslation.Core/ImageOcrTypes.cs`：`OcrRequest(byte[] PngBytes, string SourceLanguage)`、`OcrResult(string Text, long ElapsedMs)` 带 `Error`/`Succeeded`、`interface IOcrProvider : IDisposable`。

新文件 `src/FastTranslation.Providers.QwenMt/GatewayOcrProvider.cs`，与 `GatewayImageTranslationProvider` 同构：网关不接（未登录/无令牌）或额度用尽 → 安静回落自己 Key；两条都失败报自己 Key 的错。

### 7.3 为什么必须新开 `/v1/ocr` 而不是复用 `/v1/chat/completions`

现有 `GatewayEndpoints.ChatCompletions` 用 `ReadChatShape(body)` 累加 `messages[].content` 为**字符串**的长度。多模态请求的 `content` 是数组，`ReadChatShape` 读不到字符 → `chars <= 0` → **400 `text_required`**。而且 `Pricing.Table` 里没有 `qwen-vl-ocr` 条目，`Pricing.For` 会静默回落到 `qwen-mt-flash` 的价格——等于白嫖。

所以：新增 `POST /v1/ocr` 路由 + `Pricing.Table` 加 `["qwen-vl-ocr"] = new("qwen-vl-ocr", 0.043m, 0.072m, 0m)`（华北2 北京，输入 $0.043/百万 token 折人民币约 0.31 元、输出 $0.072 约 0.52 元；表里按 CNY 填，实现前用当月价目表核对一次）。

配额等价字符：图片翻译用 `gateway.ImageQuotaChars > 0 ? : 1000`，OCR 沿用同一原则，一张截图按同样 1000 字符记额度。

### 7.4 结果窗改造

`src/FastTranslation.Platform.Windows/ImageResultWindow.cs`：

- 三个 pill 变四个：`复制图片` / `另存为…` / **`保存到单词本`** / `关闭`。
- 图片下方新增一块：`识别到的原文` 标签 + 一个 `TextBox`（多行、可编辑、`MaxHeight` 约 120px、`AcceptsReturn`）。
- 识别未回来时文本框显示「正在识别…」且只读；回来后填入文本、转为可编辑。
- 新增 `ShowResult(byte[]? imageBytes, string caption, string? recognizedText, bool ocrPending)` 重载，保留旧的 `ShowResult(byte[], string)` 委托给新重载（`App.xaml.cs:187-190` 那个 lambda 要跟着改）。
- 编辑过原文再点保存 → **重新翻译一次**（约 1 秒，按钮转圈禁用）；没编辑 → 直接用已拿到的译文，不发请求。

### 7.5 `origin_app` 的取值时机（易错点）

`origin_app` 必须记「用户在看哪个应用的截图」，不是 `FastTranslation`。而 `ScreenRegionPicker.PickAsync` 会弹全屏遮罩，遮罩一出现前台就变成我们自己。

因此：**在 `RunAsync()` 开头、`PickAsync` 之前**读 `ForegroundInfo.ProcessName()`，把这个值一路带到保存动作。写实现时若发现值是 `FastTranslation`，就是这里错了。

### 7.6 `ImageTranslationCoordinator` 的改动

`src/FastTranslation.App/ImageTranslationCoordinator.cs` 现在是一条单链 `PickAsync → TranslateImageAsync → _present`。改成：

```csharp
var captured = await ScreenRegionPicker.PickAsync(_lifetime.Token);
if (captured is null) return;
var originApp = /* 已在 PickAsync 之前读过 */;

var imageTask = _provider.TranslateImageAsync(imageRequest, _lifetime.Token);
var textTask  = RecognizeAndTranslateAsync(captured.PngBytes, source, target, _lifetime.Token);
await Task.WhenAll(imageTask, textTask);
// 组装 ImageCaptureResult 后交给展示回调
```

新增内部类型 `ImageCaptureResult(ImageTranslationResult? Image, string SourceText, string TargetText, string? TextError, string OriginApp)`。

`Interlocked.CompareExchange(ref _busy, 1, 0)` 防重入保留不动（两个遮罩会互相把对方截进图里）。

## 9. 错误处理

| 场景 | 表现 |
|---|---|
| OCR 失败、图片翻译成功 | 照常出译图；识别框显示原因；保存按钮置灰 |
| OCR + 翻译成功、图片翻译失败 | 出纯文本结果窗（无图区）；保存可用 |
| 两条都失败 | 托盘气泡，同现状 |
| 未登录点「保存到单词本」 | 结果窗提示「先在账号里登录,保存的单词才能跨设备同步」并**切到主窗口套餐页**（`ShowPage(MainPage.Plan)`；原实现是弹 `AccountWindow`，见 `App.xaml.cs:637-642`） |
| 未订阅（`subscription_required`） | 显示错误文案并切到套餐页（原 `OnSaveRequested` 弹窗行为同上一行） |
| 队列为空 | 复习窗空态，不是错误 |
| 评分请求失败 | 详情页 `DetailStatus` / 复习窗顶部一行红字；卡片留在原张，按钮恢复可点 |

**服务端不静默吞错**：`POST /review` 的任何 4xx 都带现有 `ErrorResponse` 形状（`error` + 可选 `message`），客户端 `MapFailure` 已有对应映射。

## 10. 计费

- OCR 走 `/v1/ocr`，与 `/v1/image` 同构：成功才记账，失败原样转发上游状态码**且不计费**。

## 13. 竞品位置（为什么值得做）

2026-10 核查的结论，作为本设计的产品依据：

- 「三项全齐」（即时翻译 + 截图翻译 + 复习）在 Windows 桌面只有 **欧路词典** 与 **有道翻译桌面版** 两家。
- 开源生态里 A+B 有 5 家（Easydict、Pot、STranslate、沙拉查词、沉浸式翻译），但**有真 SRS 的只有陪读蛙 Read Frog 一家，且限浏览器**；B+C 组合为 **0**。
- 「生词本」在中文产品文案里严重通胀：要么是记忆曲线 + 主动回忆测验（欧路、有道），要么是纯收藏夹（腾讯翻译君、Bob、Easydict、STranslate），要么完全没有（DeepL、知云、PowerToys、QTranslate）。**没有一家提供独立的「今日复习」面板**。
- 三个可正面超越的点：①学习单位是句/段而非单词卡（`NoteClassifier` 已把短语和整句当一等公民）②语境自动附着（`origin_app` 记应用名而非窗口标题，隐私友好且够回忆）③LLM 译文本身即参考译文，可直接参与自测。

**不做的事**：不正面拼欧路的 30 万词库，不拼有道的语种覆盖。护城河在「Windows 系统级闭环 + 以句为单位」。

## 14. 风险与残留

| 风险 | 处置 |
|---|---|
| OCR 对长截图/多列排版识别质量未知 | 结果窗的识别文本**可编辑**，用户能改；改了再保存会重新翻译 |
| 一张长截图产生一条几百字的「语句」，复习时卡片过长 | 本次接受（D6）；卡片区滚动，`MaxHeight` 限制高度。下一版考虑分句 |
| `qwen-vl-ocr` 单价未在当月价目表逐字核对 | 实现前核一次；`Pricing` 表填错会静默错账 |
| 服务端列序扩展容易漏改 `ReadNote` / `INSERT` / `SELECT` 三处 | 实现时先改 SELECT 列表，再改 `ReadNote`，最后改 INSERT；迁移测试覆盖老库 |
| `origin_app` 取成 `FastTranslation` | 见 §7.5，在 `PickAsync` 之前读 |
| 每张截图 3 次上游调用，网络慢时结果窗等待变长 | 图片与 OCR 并行；任一先回来先渲染，后回来的补上 |
| 每日新词上限 20 写死在客户端 | 暂不进设置页（YAGNI）；要改时加设置项并随 query 传 |
| **主窗口重写会丢掉现有细节**（`Body_PreviewMouseWheel` 嵌套滚动、`InputHint` 叠层、`FocusInput()`、`Ctrl+Enter`） | 逐项列在 §8.3 与实现计划里，搬完用截图 + 手工点一遍核对；`MainWindow` 的 182 行里只有 UI 装配逻辑，业务方法（`RunTranslationAsync` 等）整体平移不改 |
| **`NotesWindow` 拆页后 `_shelf` 状态机废弃**，但 `ReplaceRow` 等逻辑要保住 | 先搬 `ReplaceRow` / `LoadAsync` 到 `NotesPage`，再从 `NotesWindow` 删；删之前 grep 确认无其他引用 |
| **四扇窗合成一扇后，`App.xaml.cs` 的 11 处 `Show*` 调用点要全改** | 用 `ShowPage(MainPage.X)` 统一入口，编译期就能查出漏改（旧方法直接删除，不留兼容层） |
