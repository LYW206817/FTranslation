## 1. 要解决的问题

产品现在有 **A 即时翻译**（选中文字 → 浮动工具条 → 结果卡）和 **B 截图翻译**（框选屏幕区域 → qwen-mt-image 出译图），**C 只完成了半个**：能保存到三个单词本，但**没有任何复习机制**。

对着市面上的同类软件看，这个缺口很具体：

| 能力 | 欧路词典 | 有道 | STranslate | **我们（改造前）** |
|---|---|---|---|---|
| 即时/划词翻译 | 有 | 有 | 有（增量划词） | **有** |
| 截图翻译 | 弱（要先截图再切回） | 有 | 有（微信 OCR 离线） | **有** |
| 生词本 | 最强（30 万词库 + 云同步） | 有 | 有本地备份 | **有（只能存，不能复习）** |
| 复习调度 | 艾宾浩斯曲线 | 记忆曲线 + active recall | **无 SRS 证据** | **无** |

三项全齐的只有欧路与有道两家，护城河是十几年积累的词库与语种覆盖——正面拼词库赢不了。真实空位有三个：

1. **学习单位可以是「句/段」而不是单词卡**：`NoteClassifier` 已经把短语和整句当作一等公民（`kind` = word/phrase/sentence）。
2. **语境自动附着**：存的时候记下 `origin_app`（前台进程名，**刻意不取窗口标题**，见设计 §8），复习时能说「这句你是在 Word 里遇到的」。
3. **LLM 译文本身就是学习材料**：可以直接当参考译文参与自测，不需要人工维护释义。

本计划交付的正是 **C 的后半个**，并把 A/B/C 收进一个单窗口。

## 3. 总体设计

### 3.1 一个窗口，七个页面

`MainWindow` 从「翻译窗口」变成**宿主**：左侧 172px 侧栏 + 右侧 `ContentControl` 页面宿主，默认 1040×660，最小 900×600。

| 页 | 内容 | 数据来源 |
|---|---|---|
| 首页 | 输入框（`InputBox`）、目标语言、翻译按钮、结果卡、**今日复习入口** | 本地 `TranslationService` |
| 单词 / 短语 / 语句 | 同一个 `NotesPage` 的三份实例，只差 `kind` | `NotesApiClient.ListAsync` |
| 套餐 | 当前计划、用量、兑换码 | `AccountCoordinator` |
| 设置 | 原先的 `SettingsWindow` 内容 | `AppSettings` |

三个旧窗口（`NotesWindow`×3、`SettingsWindow`）删除，逻辑搬进对应 Page 的 code-behind。

### 3.2 四档复习的调度

复习状态是 `notes` 表上的**六列**，不是新表：

| 列 | 类型 | 含义 |
|---|---|---|
| `stage` | INTEGER NOT NULL DEFAULT 0 | 0 = 从未评分；1~7 = 台阶 |
| `due_at` | INTEGER NOT NULL DEFAULT 0 | unix 秒；stage 0 恒为 0 |
| `last_grade` | TEXT NOT NULL DEFAULT '' | `forgot` / `fuzzy` / `familiar` / `known` |
| `review_count` | INTEGER NOT NULL DEFAULT 0 | 累计评分次数 |
| `lapses` | INTEGER NOT NULL DEFAULT 0 | `forgot` 次数 |
| `reviewed_at` | INTEGER NOT NULL DEFAULT 0 | 上次评分时间 |

台阶表（**产品常量，不是可调参数**）：

| 台阶 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 间隔 | 未排期 | 10 分钟 | 1 天 | 3 天 | 7 天 | 14 天 | 28 天 | 56 天 |

四档映射（`ReviewSchedule.NextStage`）：

| 当前档 \ 评分 | 忘记 | 模糊 | 熟悉 | 记住 |
|---|---|---|---|---|
| 0（新） | 1 | 2 | 3 | **4** |
| 1~3 | 1 | 2 | 3 | **4** |
| 4 | 1 | 2 | 3 | **5** |
| 5 | 1 | 2 | 3 | **6** |
| 6 | 1 | 2 | 3 | **7** |
| 7（封顶） | 1 | 2 | 3 | **7** |

两条规则值得单独说：

- **`记住` 首答直接跳 7 天**（stage 4）——用户已经会了，没有理由今天再出现一次；之后每次 `记住` 上一级，封顶 56 天。
- **所有降级的下限是 stage 1**：stage 0 专门表示「从未评分」，是一条**独立于时间**的队列，由每日新词配额（默认 20）喂进复习窗。这样被忘记的词不会掉回「新词堆」重刷一遍。

### 3.3 队列与今日限额

复习窗一次展示两类卡：

- **到期（Due）**：`stage >= 1 AND due_at <= now`，按 `due_at` 升序。服务端用部分索引 `ix_notes_user_due`。
- **新词（Fresh）**：`stage = 0 AND created_at >= dayStart`，按创建时间升序，条数受 `newLimit` 约束；`freshQuota = max(0, newLimit - 今天已入队的新词数)`。

`dayStart` 由**客户端**算自己的本地零点并作为查询参数传上去——服务端永远不猜时区（设计 §5.4）。

### 3.4 截图 OCR

截图翻译现在的链路是「截图 → qwen-mt-image → 译图」。本轮加一路并行的 OCR：

```
截图 ──┬─→ qwen-mt-image（译图）──→ 结果窗「译图」
       └─→ /v1/ocr（qwen-vl-ocr）─→ 结果窗「识别文本」
```

为什么**必须新开端点**而不能复用 `/v1/chat/completions`：`GatewayEndpoints.ReadChatShape` 只累加 `content` 是字符串的 `messages[]`，OCR 的 `content` 是 `[{type:"image_url"}]` 数组，读出来 `chars == 0` 直接被 `400 text_required` 挡掉；而且 `Pricing.Table` 里没有 `qwen-vl-ocr`，`Pricing.For()` 会静默回落到 `qwen-mt-flash` 的价格——等于白嫖上游。所以 OCR 必须有独立的计费入口。

识别出的文本在结果窗呈现四个 pill：**全部存为语句** / **存为单词** / **复制** / **翻译这段**。

**Phase A 实测（2026-10-29）**：`dotnet build` 0 警告 0 错误；`dotnet test` 408 → **503 全绿**（Core 192 / QwenMt 58 / Platform.Windows 87 / Server 166）。

执行中发现两处与计划的偏差，已回写实现计划：

1. **服务端不引用 `FastTranslation.Core`**（`FastTranslation.Server.csproj` 只有 `Microsoft.Data.Sqlite`）。所以按仓库既有惯例（`Domain/NoteKind.cs`、`Domain/NoteClassifier.cs` 本来就是客户端同名类型的镜像），新建 `server/FastTranslation.Server/Domain/ReviewSchedule.cs` 作为权威副本，客户端那份只负责按钮上「7 天后」这类文案。
2. **`ix_notes_user_due` 不能写在 `Schema` 常量里**：老库还没有 `due_at`，`Schema` 是单次 `ExecuteNonQuery`，建索引会先炸，`EnsureColumn` 根本轮不到执行。索引改到 `Initialize()` 里、`EnsureColumn` 之后创建。

## 5. 前后端契约

新增两个端点，字段名 camelCase 是客户端契约（`Contracts.cs` 文件头注释：改名即破坏客户端）。

```http
GET /api/v1/notes/review?dayStart=1793318400&newLimit=20&limit=50
Authorization: Bearer <access_token>

200 {
  "due":   [ { "id": "...", "kind": "word", "sourceText": "...", "targetText": "...",
               "stage": 4, "dueAt": 1793404800, "lastGrade": "known",
               "reviewCount": 1, "lapses": 0, "reviewedAt": 1793318400, ... } ],
  "fresh": [ { ... "stage": 0 ... } ],
  "dueTotal": 1, "freshQuota": 18, "limit": 50, "newLimit": 20
}
```

```http
POST /api/v1/notes/{id}/review
Authorization: Bearer <access_token>
Content-Type: application/json

{ "grade": "known" }        // forgot | fuzzy | familiar | known

200 NoteDto                  // 已更新后的整条，客户端直接替换本地卡片
```

错误码：`grade_invalid`(400) / `note_missing`(404，**别人的卡也是 404，不透露存在性**) / `subscription_required`(403) / `account_disabled`(403)。

## 6. 测试策略

- **纯函数优先**：`ReviewSchedule` 的 8×4 转移表用 `[Theory]` 逐格断言，不写「凑数」的集成测试。
- **时间可控**：`ServerDatabase` 已支持注入 `TimeProvider`；`NotesReviewTests` 里的 `ManualTimeProvider` 用来推进「到期」而不 sleep。
- **迁移必测**：`Migration_OldDatabaseGainsTheReviewColumns` 手工建 v47 形状的 `notes` 表，跑 `Initialize()`，断言六列到位且**遗留行变成 stage 0 的未评卡**。
- **隔离**：每个用例独立账号（`NotesTestHelpers.SignedInNotesClientAsync`），测试之间看不见彼此的笔记。
- **UI 必须给像素证据**：`tools/qa/shot-*.ps1`，不说「已改好」。
- 基线纪律：开工 408 → Phase A 503，后续每阶段只增不减。

一次改动算完成，需要同时满足（AGENTS.md「完成的标准」）：

1. `dotnet build FastTranslation.slnx -c Release` **0 警告 0 错误**；`dotnet test` 全绿，新增行为带新测试。

   - 主窗口六页各一张（首页 / 单词 / 短语 / 语句 / 套餐 / 设置）

5. 临时文件清理干净，`git status --short` 里没有意外文件。

## 12. 后续增补：账号与套餐拆页（2026-10-29）

原始需求之后追加的一条：「套餐页里的账号信息、剩余额度、额度重置过程混在一起，读起来费劲」，要求侧栏拆出一页「账号」，把「我是谁 / 还剩多少」和「买什么 / 怎么算」分开。

### 12.1 拆页后的分工

| 页面 | 回答的问题 | 内容 |
|---|---|---|
| 账号 | 我现在是什么身份、还剩多少 | 头像 / 名称 / 套餐角标 / 邮箱；刷新、退出登录；当前套餐与有效期；本月与今日剩余额度条；改名称；改密码；数据说明 |
| 套餐 | 我能买什么、额度怎么算 | 订阅卡（年付 ¥144 / 月付 ¥18）、包括什么三条、本月与今日用量、额度怎么重置（月 / 日 / 复习队列）、激活码 |

判定口径：一页只回答一个问题。原来套餐页里那张横跨整行的账号卡同时承担身份、额度、退出登录三件事，且压在价格表上方，两个意图互相干扰。

### 12.2 新增的服务端契约

| 方法 | 路径 | 请求 | 成功 | 失败 |
|---|---|---|---|---|
| PATCH | `/api/v1/account/profile` | `{"displayName":"永威"}` | `200 AccountDto` | `400 display_name_too_long` / `400 display_name_invalid` |
| POST | `/api/v1/account/password` | `{"currentPassword","newPassword","deviceFingerprint","deviceName"}` | `200 AuthResponse`（新的一对令牌） | `400 password_mismatch` / `400 password_too_short` / `400 password_unchanged` |

- `users` 表新增 `display_name TEXT NOT NULL DEFAULT ''`；空串表示「没设名称」，界面回落显示邮箱
- 改密码同时撤销该账号全部 refresh token：本机拿到新的一对所以不掉线，别的设备下次刷新时被拒
- 名称 24 字符上限、拒绝控制字符，理由是这个值会进窗口标题区与侧栏，换行会把布局撑坏

### 12.3 验收标准

1. 侧栏顺序：首页 / 单词 / 短语 / 语句 / 复习 ── 账号 / 套餐 / 设置
2. 账号页已登录态能看到名称、套餐、邮箱、本月与今日剩余额度；未登录态左表单右说明
3. 改名后头像首字、名称、侧栏底部账号行同步更新，状态行提示「名字已保存。」
4. 改密码后本机仍可用，旧密码登录失败，其它设备的 refresh token 被撤销
5. 套餐页不再出现身份信息，只有价格、用量、重置说明与激活码
6. 截图：账号页已登录 / 改名后 / 未登录 / 深色 / 套餐页各一张（1820×1155）
7. `dotnet build` 0 警告 0 错误；`dotnet test` 全绿
