## v81 备案上线一键脚本 go-live.sh，并修掉升级会覆盖 Caddyfile 的隐患（1.5.0）

### 为什么这样改

备案号下来那一刻要连做六件事：云解析加记录、替换 `Caddyfile` 占位符、填页脚备案号、`caddy validate`、`systemctl enable --now caddy`、逐项验收。手工做最容易漏两处：**页脚备案号**（境内站点必须展示，漏了是合规问题）和**域名是否真的解析到这台机器**（指错了会先怀疑证书，白查半小时）。所以收成一条命令，带只读的 `--dry-run`、五项断言和回滚命令。

顺带修掉一个真缺陷：`install.sh` 原来无条件 `install -m 0644 "$HERE/Caddyfile" /etc/caddy/Caddyfile`，而上传目录里的模板永远带占位符 —— 也就是说**上线后任意一次升级都会把配好的 Caddyfile 换回占位符，接着那段占位符检测把 caddy 停掉，网站直接下线**。现在检测到已配好的 Caddyfile 就保留（要重铺模板用 `FT_FORCE_CADDYFILE=1`）。

### 脚本

`deploy/go-live.sh`（218 行，LF，`set -euo pipefail`）：

- 参数：`--domain`（默认 ftranslation.cn）、`--email`、`--icp`、`--expect-ip`、`--skip-icp`、`--dry-run`
- 前置体检（任一不过直接退出，不改文件）：`getent ahostsv4` 确认解析、`--expect-ip` 比对、`ss` 确认 80/443 没被非 caddy 进程占着、占位符现状
- 变更：`cp -a` 留 `.bak` → `sed` 两处占位符 → 页脚 `__ICP_NUMBER__` → `caddy validate` → `enable --now`（已在跑则 `reload-or-restart`）
- 等待：轮询 `https://<域名>/health` 至多 90 秒（ACME HTTP-01 首次签发要几十秒）
- 断言五项：80 回 301/308；`/health` 含 `"ok"`；证书 `subject`/`enddate`（有 openssl 时）；页面不含 `__ICP_NUMBER__` 且含 `beian.miit.gov.cn`；页面含传入的备案号
- 收尾：打印 `systemctl is-enabled/status caddy`，失败时打印一行回滚命令

### 验证

- `bash -n deploy/go-live.sh` 与 `bash -n deploy/install.sh` 均通过；两个文件确认 LF（无 CR）。
- **生产机上的 `--dry-run` 没跑成**：本机当前出口 IP 是 `223.104.121.58`（武汉移动 4G），而安全组 22 只放行 `59.173.184.134/32`，`ssh root@114.55.166.224` 直接 `Connection timed out`，`python socket.connect` 探测 22 同样超时。脚本的真机行为等能 ssh 时补验（这是本次交付的已知不足，不写成已验证）。
- 因此本次没有新增/修改任何 C# 代码，`dotnet build` 与 573 项测试的结论沿用上一版（未受脚本改动影响）。

### 残留风险

1. `--icp` 是自由文本，直接进 `sed s/__ICP_NUMBER__/<值>/`：值里若含 `/` 会让 sed 报错（备案号字符集是汉字+数字+`号-`，正常不会触发；真要含就在脚本里换分隔符）。
2. `go-live.sh` 只改服务器上的 `/var/www/fasttranslation/index.html`，不改仓库里的 `site/index.html`：下次 `install.sh` 整目录同步站点会把页脚覆盖回占位符。脚本收尾已经打印这条提醒，但仍需人工提交一次仓库副本。
3. DNS 传播有 TTL，`--expect-ip` 可能在记录刚加时失败（脚本报「wrong record or stale cache」），等 10 分钟重跑即可，不是脚本缺陷。
4. 脚本假设 Caddy 用默认的 `/etc/caddy/Caddyfile` 与静态根 `/var/www/fasttranslation`（与 `install.sh` 的两个变量一致）；换路径要同步改两处常量。
5. 备案仍在管局审核：2026-10-29 12:48 提交、订单 2038868333211，页面显示 1~4 步（提交审核 / 阿里云初审 / 待提交管局 / 工信部短信核验）已全部完成，当前停在第 5 步「管局审核」，预估 10 个工作日、法定最长 20 个工作日。预计出号窗口 11-12 前后（Workday 计数从 10-30 起算：7 个工作日 ≈ 11-09，10 个 ≈ 11-12，20 个 ≈ 11-26）。
## v81 语音额度可突破与识别语种错位（1.5.0 修复）

### 为什么

代码审查（2026-11-02）发现两个 P0：

1. **额度可被单会话顶穿十几倍**。`SpeechEndpoints` 只按「最小会话」(MinSeconds×QuotaCharsPerSecond=200 字符) 做额度预检，而会话硬顶是 1800 秒、记账只在 `DashScopeSpeechGateway` 的 finally 里一次性记 36,000 字符。Free 日额度 2,000 → 一场会话就超日上限 18 倍。限流器只数每分钟请求数（40/min），没有并发会话上限，同一账号可以同时开几十条各自按 200 预检的会话；`ReadTodayCostMicros("speech")` 又只在会话开始读、结束才写，并发时集体读到 0。三道闸全部形同虚设。
2. **识别语种提示方向错**。客户端把「译成哪种语言」当作 `language` 发给服务端，服务端原样塞进 DashScope 的 `language_hints`。选「译成中文」时，英文音频被硬按中文识别——字幕从第一句就开始错。

### 服务端改了什么

- 新增 `Domain/SpeechQuota.cs`：纯函数 `SessionSeconds(remainingChars, charsPerSecond, minSeconds, maxSeconds)` = `max(min, min(剩余可讲秒数, 硬顶))`。额度算错直接等于烧钱，所以按 `QuotaPolicy` 的做法抽成纯函数 + 单测。
- 新增 `Gateway/SpeechSessionLimiter.cs`：按账号的并发会话计数（`TryEnter`/`Exit`，`ConcurrentDictionary` + CAS 循环，`max≤0` 不限制）。`SpeechOptions.MaxConcurrentSessionsPerUser` 默认 1；`Program.cs` 注册单例。
- `SpeechEndpoints`：额度决定后先算 `remaining = min(RemainingMonthly, RemainingDaily ?? int.MaxValue)`，再算 `sessionSeconds = SpeechQuota.SessionSeconds(...)`；`TryEnter` 失败 → 429 `speech_busy`；「非 WS→400 / Accept / RelayAsync」包进 `try/finally { sessions.Exit(userId) }`，把 `sessionSeconds` 传进中继。
- `DashScopeSpeechGateway`：
  - `RelayAsync` 多收一个 `sessionSeconds`，硬顶用它（不再直接用 `MaxSecondsPerSession`）。
  - 记账从「finally 一次性」改成 `Bill(...)` 局部函数：每收到一帧 `result-generated` 就按**增量**（deltaSeconds / deltaTokensIn / deltaTokensOut）插一行 `usage_events(source='speech')`；finally 只补足 `MinSeconds` 的差额。日预算与额度闸门因此看到的是实时花费，客户端半路跑掉也不会丢账。
  - 会话硬顶到期时给客户端发一条 `{"type":"error","code":"session_timeout",...}`，再关流——否则用户只看到「连接中断」，会以为是网络问题。
  - **关流收口到 `RelayAsync` 的 finally**：上游泵不再自己 `CloseAsync`。原先两处都在关，错误帧和关闭抢时序，实测时好时坏（新增测试在并行负载下就会收到 Close 而不是错误帧）。

### 客户端改了什么

- `GatewaySpeechTransport` 的 start 帧只报 `sampleRate`，不再带 `language`；`SpeechSessionOptions` 删掉 `TargetLanguage`（识别语种必须由 ASR 自己判断，译成哪种语言由翻译回调决定），四处构造点同步收窄。
- 升级前探测复用应用唯一的 `_gatewayHttp`（原来每次会话 `new HttpClient`），并用 10 秒的 linked CTS 限时——共享客户端的 45 秒超时不能拖着开始会话。
- 采集停止移出 UI 线程：`Stop()` 内部 `Join` 采集线程最多 2 秒，在 UI 线程上同步等会把窗口冻住（结束会话、切换设备两条路径都改）。
- `AudioResampler.MaxOutputBytes(inputSamples)`：按「输出帧数×2+余量」算精确上限，替换 `floats.Length/2*6+64` 这种 9 倍拍脑袋分配（48k 立体声 100ms 块只需 3.2KB，原来每块分配 28.8KB，一秒约 300KB gen0 垃圾）。

### 测试

- 新增 `SpeechQuotaTests`（折算边界 + 并发闸门 3 条）、`Asr_returns_429_when_the_account_already_has_a_session`、`Session_timeout_tells_the_client_why_it_stopped`、`MaxOutputBytes_matches_what_a_block_actually_produces`。
- 断言 `run-task` **不再**含 `language_hints`（锁住 P0-2）。
- 顺手修了一个测试隔离坑：两个语音中继测试的 `SqliteConnection.ClearAllPools()` 会清掉**整个进程**的连接池，并行跑的其他测试打到失效连接上，表现为 `AccountProfileTests` 偶发登录 500。去掉后 Server 套件连跑 3 次稳定。
- 全量：`dotnet test` **702 通过 0 失败**（Core 302 / Platform.Windows 97 / Providers.QwenMt 95 / Server 208），连跑 2 次一致；Release build 0 警告 0 错误。

### 残留

- **重采样没有抗混叠低通**（设计 §5.1 写的是 3 抽头滑动平均，实现是直接线性插值）。48k→16k 会有一部分高频折回，可能让 ASR 把气声、齿音听错。这段改动会改变输出样本值，需要拿真实音频 A/B 才敢定，留到端到端真声联调一起做。
- `SpeechTranscriptService.DroppedCount`（队列满丢批次数）仍未上屏，用户看不出「字幕丢了几句」。属于体验项，等真声联调后再定是否显示。
- 真声端到端（播视频→看字幕）、`target_lang="auto"` 链路、生产 wss 腿仍待联调/备案。
## v82 语音链路剩余隐患收口：墙钟计费、跨帧 JSON、残留样本与后台任务异常（1.5.0 修复）

用户问「隐患都修复了吗?」之后逐条核对 v81 的遗留项,本版修掉 6 处,另 1 项明确不做并给出理由。

### 改了什么

1. **上游一条 usage 都没报时按墙钟计费**（`server/FastTranslation.Server/Gateway/DashScopeSpeechGateway.cs`）。
   之前只有 `latestUsage is { } usage` 一个分支:连接刚建就被砍、或全程静音时一帧 usage 都收不到,于是一分钱不记——
   预检已经放行、上游 ASR 算力已经花掉,这是可以白嫖的口子。现在 else 分支按
   `DateTimeOffset.UtcNow - startedAtUtc` 取秒数(上限 `sessionSeconds`)、不足 `MinSeconds` 按 `MinSeconds` 记。
2. **上游 JSON 跨帧拼接**（同上,`PumpUpstreamAsync`）。`ReceiveAsync` 只读一帧,`received.EndOfMessage=false` 时
   旧实现把半截 JSON 直接丢给 `JsonDocument.Parse`;而 DashScope 的长句终稿带 `words[]`、单帧可达数十 KB,
   一旦分帧就是「静默丢句」。现在用 `MemoryStream` 累积到 `EndOfMessage` 再解析。
3. **收尾补发重采样器残留样本**（`src/FastTranslation.App/App.xaml.cs` 的 `EndSpeechSession`）。
   `AudioResampler` 内部压着不足一块的样本(最多 100ms),之前从不调用 `Flush`,每段话的尾巴都被吞掉。
   现在结束前 `Flush` 一次并 `PushAudio`。
4. **后台任务异常不再静默**（同文件新增 `Observe(Task, string)`）。语音链路有 4 处 fire-and-forget
   (`StartSpeechSessionAsync`/`RestartSpeechCaptureAsync`/`StopAsync`/`DisposeAsync`),以前任一抛出都无人观察,
   用户只看到窗口一直转圈。现在统一 `ContinueWith(OnlyOnFaulted)` 回 UI 线程显示原因;`Task.Run` 里的
   `capture.Stop()/Dispose()` 也补了 `ObjectDisposedException/InvalidOperationException` 兜底。
5. **被丢弃的句子要说出来**（`SpeechWindow.EndSession(string? error, int dropped)`）。
   `SpeechTranscriptService.DroppedCount` 之前只存在不上屏,队列满丢句时用户只看到字幕缺词、以为模型漏译;
   现在结束态显示「已结束(N 句因处理不过来被丢弃)」。
6. **浮窗不再抢焦点**（`ShowSpeechWindow` 去掉 `Activate()`）。开始语音时用户多半正在打字,抢焦点会打断输入;
   窗口置顶 + `Show()` 已足够可见,要拖动或点关闭时用户自己会点它。

### 明确不修的一项

**重采样仍无抗混叠低通**(`src/FastTranslation.Core/Audio/AudioResampler.cs:94` 直接线性插值,设计 §5.1 曾提 3 抽头滑动平均)。
不做原因:48k→16k 是 3:1 抽取,理论上 8 kHz 以上会折回;但收益只能靠真机真声 A/B(看 ASR 是否正确率更高),
当前没有可用额度做端到端真声验证,先加一版无法证明收益的滤波只是增加回归面。已列入残留风险,端到端联调时一并验。

### 验证

- `dotnet build FastTranslation.slnx -c Release` → 0 警告 0 错误(**构建前必须先停应用与本地服务**,否则
  MSB3026/MSB3021 锁文件)。
- `dotnet test` → **704 通过 0 失败**(Core 302 / Platform.Windows 97 / Providers.QwenMt 95 / Server 210);
  Server 由 208 增至 210,正是本版新增的 `Bills_wall_clock_when_upstream_never_reports_usage` 与
  `Assembles_json_split_across_text_frames`。
- 无界面布局改动,截图沿用 v79(`SpeechWindow` 只改了结束态文案)。


## v83 · 设置页新增强调色：电光蓝 / 湖蓝 / 雾光紫（1.5.0）

### 为什么

用户要「电光 / 湖蓝 / 雾光紫」三种色号都能在设置里选（原话见 m05854）。此前主题只有浅色/深色两档，

不进仓库）做出来才看清：用户真正要的不是新布局，而是**把色相抽成独立思考的第二维**。

### 怎么做的

- **强调色与明暗正交**：`AccentColors`（`src/FastTranslation.Platform.Windows/ThemePalette.cs`）只装品牌色一族九项
  （Brand / BrandHover / BrandPressed / BrandFill / BrandFillHover / BrandText / OnBrandText / BoltFrom / BoltTo），

  无需迁移），`App.OnStartup` 里 `ThemeBridge.Apply(ThemePalette.Resolve(_settings.Theme), _settings.Accent)` 生效。
  属性页提示语同步改成「主题、强调色与热键均在下次启动后生效」（**v84 起改成选完立即生效**，见下节：

### 界面

## v84 · 主题与强调色选完即生效，不再要求重启

### 为什么

用户看完 v83 直接问「怎么还重启生效呢？不能保存生效吗」。原来那句「下次启动生效」是从 v24 沿用下来的
（`docs/IMPL.md:351` 当时判断实时换肤要把 94 处 `StaticResource` 全改 `DynamicResource` + 调色板可变 + 窗口重建）。
但这两件事其实早就做完了：v24 起 XAML 里每处画刷引用都是 `{DynamicResource …}`，且画刷带 `po:Freeze="False"`，
`ThemeBridge.Set` 一直是**就地**改 `SolidColorBrush.Color`（`src/FastTranslation.App/ThemeBridge.cs:64-81`）。
也就是说缺的只有一次调用——画刷树不用重建，标题栏要单独再推一次 DWM。

### 怎么做的

## v89 · 去掉全局软件渲染，画刷一律冻结替换（1.5.0 性能线）

**症状**：点侧栏要等一会儿才跳页，页内上下滚动明显掉帧。

**根因一：整个进程被强制成软件渲染。** `src/FastTranslation.App/SoftwareRender.cs` 用 `[ModuleInitializer]` 把 `RenderOptions.ProcessRenderMode` 设成 `SoftwareOnly`——这是 M0 时期为压住 D3D 路径约 77MB 私有工作集做的取舍，注释里写着「在 App.OnStartup 里设太晚，D3D 在那之前就已初始化」。代价是整窗每一帧都由 CPU 光栅化：在 2548×1600 的窗口上，一次换页或一格滚动就是 400 万像素的重新绘制。文件已删除，回到 WPF 默认渲染路径。

**根因二：设计 token 是可变画刷。** `src/FastTranslation.App/App.xaml` 的 19 个画刷带 `po:Freeze="False"`，`ThemeBridge.Set` 走「就地改 `Color`」分支，于是这些画刷永远不会被冻结。冻结的 `Freezable` 才能被渲染线程直接复用，可变画刷每帧都要重新序列化一遍。现在改成整支替换新的冻结画刷，`po:Freeze="False"` 与 `xmlns:po` 一并删掉；所有引用本来就是 `{DynamicResource …Brush}`（全仓只剩 `Pages/MainPage.xaml:26` 一处 `StaticResource PillDot`，它的填充也是 DynamicResource），换条目后元素自动重新解析。

**本机测量（`FT_UITEST=nav`，窗口 2548×1600 物理）**

- 渲染层级 `tier=2 mode=Default`，即硬件路径已生效；换页帧时 pass=0 仍是 40–124ms、pass=1 22–40ms，与软件渲染时同一量级 ⇒ 这台机器的会话挂在 Oray/Idd 虚拟显示适配器上，present 本身是瓶颈，**这组数字不能代表用户本地直连显示器的观感**。

## v95 语音字幕：修掉那只「一次性闹钟」——译文永不回填的真因

v94 之后语音已经能连上、能识别出正确原文，但译文一格都不出。定位到根因是一行定时器的写法。

**为什么这样改**：`SpeechTranscriptService` 构造函数里 `CreateTimer(DrainDebounce, null, TimeSpan.FromMilliseconds(DebounceMs), Timeout.InfiniteTimeSpan)`——dueTime 从**构造那一刻**起算，period 无限，即一次性闹钟。而这个服务是在 `StartSpeechSessionAsync` 里、会话开始的那一刻才构造的：500ms 后唯一那次触发时 `_pending` 还是空的（`batch.Count == 0` 直接 return），此后没有任何一处再 `Change` 它。于是整个会话期间所有 `final=true` 的终稿全部堆在 `_pending` 里，等一次再也不会来的闹钟。表现就是字幕只有原文、译文永远空白；而且因为 `RunBatchAsync` 压根没跑过，连「翻译失败」都不会发生——静默得一点痕迹都没有，这也是它难查的原因。

**为什么现有测试抓不到**：`SpeechTranscriptServiceTests` 里驱动翻译的 13 处调用**全部手动 `DrainDebounce()`**，且 `Options()` 默认 `debounceMs: 0`，连定时器都不创建。测试把坏掉的那一环整个绕开了，所以 302 个用例全绿而真实会话永远不出译文。

**改法**：定时器挂成 `Infinite/Infinite` 不自动启动，改由「终稿入队」驱动——`_pending` 从空变非空时 `Change(DebounceMs, Infinite)`。同一防抖窗口内的多句仍合并成一批送 MT（原语义不变），批被取走后下一句终稿重新计时。`Change` 刻意放在 `lock` 外：定时器回调 `DrainDebounce` 要抢同一把 `_gate`，持锁调度有自锁风险。

- **测试有效性反证**：临时把 `schedule = _pending.Count == 0` 改成 `schedule = false && …`（等价于旧的一次性闹钟行为）→ 恰好这 2 个用例失败、其余 302 个不受影响 → 证明它们真的咬住了修复点，不是空转。改回后复绿。

## v96 语音额度预检：补上免费档的日额度这道闸，别让它伪装成「点了没反应」

**为什么这样改**：`StartSpeechSessionAsync` 的开场预检只比了月度剩余额度，而服务端 `QuotaPolicy.Evaluate` 同时查月度与**每日**两个桶，免费档还有 `FreeDailyChars=2000` 这道日限。于是日额度用满、月度还剩六千多时，客户端判定「可以开始」→ 建窗口、连网关，服务端回 429 `daily_quota_exhausted`，而 429 在客户端只被翻译成「无法连接语音服务,请稍后再试」——用户看到的就是点了没反应，或者一句莫名的连接失败。v94/v95 排查期间实测撞上的正是这条。

**改法**：判定挪进 Core 的 `SpeechQuotaGate.Refusal`（纯函数，能单测），两个桶都查，返回该显示给用户的那句话；App 只负责弹气泡。门槛沿用「一分钟」而不是服务端的最小会话 200 字符——只剩十秒额度就允许开始，用户讲两句就被掐掉，体验比直接拒绝更差；客户端比服务端严不会误拒，反过来就会。额度提示同步改成两个窗口都报（`今天可讲约 N 分钟,本月约 M 分钟`），否则用户看着「本月还能讲 5 分钟」却被拒，只会以为功能坏了。

验证（用本地网关做了一次真·对照实验，两轮只差日额度一个变量）：

- **RUN A**（日额度剩 1540 ≥ 1200）：探针打到 `allow monthly=5960 daily=1540 quotaDaily=2000` → 放行，服务端收到 `GET /v1/asr - 400` 预检。
- **RUN B**（日额度剩 300 < 1200）：探针打到 `refuse monthly=5500 daily=300 quotaDaily=2000 msg=语音额度不足,今天剩余不够 1 分钟,明天恢复` → **服务端整轮零 `/v1/asr` 请求**，客户端在本地就拦住了。这正是修复前会静默失败的那个状态。
- 新增 5 个单测（`SpeechQuotaGateTests`）：月度不足、日额度不足但月度充足、付费档无日上限（`RemainingDailyChars=null`）不误拒、门槛常量。
- **测试有效性反证**：把日额度判定改成永假 → 恰好 `Daily_shortfall_refuses_even_when_the_month_still_has_room` 一个用例失败、其余 308 不动 → 证明它咬住了修复点。
- `dotnet build -c Release` → 0 警告 0 错误；`dotnet test` → Core 309 / Platform.Windows 107 / QwenMt 95 / Server 210 = **721 全绿**。

残留风险：

- 提示与判定的读值时机不同：实测 RUN B 里气泡文案读到 `daily=300`，而导航时刷新的提示显示「今天可讲约 1 分钟」，两者相差一个会话的记账。`AccountCoordinator.ReadUsageAsync` 走的是同一份会话，差异来自页面刷新与点击之间服务端又记了一次账，不是缓存 bug；但提示确实可能滞后一小段，要完全同步得让提示与预检共用一次读取。本轮没动。
- 客户端仍然看不到服务端拒绝的具体原因：429 的 `X-FT-Quota-Reason` 响应头没人读，所以除了开场预检之外的额度耗尽（比如讲到一半）仍会显示成「无法连接语音服务」。
- 本机开发库 `usage_daily` 的今日计数被本轮手动改过（当前 1700/2000），真实值已不可考；归零前的原始快照在 `server/FastTranslation.Server/data/fasttranslation.db.bak-123637`，该文件与 `data/` 都不进仓库。

## v97 网关额度：plus 按真实成本倍率记账，堵掉「低价档买高价模型」的套利

**为什么这样改**：额度单位是「字符」，但 `qwen-mt-plus` 每字符的真实成本是 flash 的 **2.68 倍**（实测 8.33 vs 3.11 微元/字符：单价 1.8/5.4 对 0.7/1.95，token/字符比取划词样本 输入 2.02、输出 0.87）。原先 `GatewayEndpoints` 不分模型、按原始字符 1:1 扣额度，等于用户把设置切到 plus，就能用 5.9 元的 88 万字符档买走 7.33 元的成本（10.9 元/200 万档亏得更多，-53%）。反方向 lite 又比它真实成本收得贵。倍率表见 `.agents/design/2026-11-03-语音额度折算率实测校验-设计文档.md`。

**改法**：额度单位统一成「flash 等价字符」。`Pricing.QuotaChars(model, rawChars)` 按表折算（flash 1.0、plus 2.7、lite 0.85，未知模型与空值按 1.0，与 `For()` 回落 flash 的口径一致），**预检与记账两处必须同时用它**——只改记账的话闸门仍按原始字符放行，plus 能把剩余额度直接透支掉。非零请求折算后至少记 1 字符：lite 倍率小于 1，不封顶会把小文本四舍五入成免费，顺手绕开额度闸门。

`MaxRequestChars` 那道检查刻意仍用**原始**字符数——它限制的是发给上游的请求体大小，不是额度。

**副作用（是想要的效果，但要知道）**：语音的译文段走的就是 `/v1/chat/completions`，所以选 plus 后语音每分钟实耗从约 1950 涨到约 **3225 额度字符**（ASR 1200 + 译文段 750×2.7）。成本口径因此对文本、语音、图片三条链路一致成立：1 额度字符 ≈ 3.1 微元。

验证：

- 新增 9 个用例（`PricingTests` 5 个折算 + `GatewayEndpointTests` 2 个端点行为 + 既有用例回归）。
- **反证**：把预检与记账两处同时退回原始字符，`PlusChat_BillsFlashEquivalentChars` 与 `PlusPrecheck_ReservesTheMultipliedQuota_WhileFlashStillFits` **各自都失败**——证明这两处分别被独立咬住，不是一个测试蒙过两处。预检那条的构造是：Free 档日额度先花掉 1800 只剩 200，同一额度下 plus（需 270）必须 429、flash（需 100）必须 200。
- `dotnet build -c Release` → 0 警告 0 错误；`dotnet test` → Core 309 / Platform.Windows 107 / QwenMt 95 / Server 218 = **729 全绿**。
- 客户端设置页模型下拉框改成「Plus(更高质量,消耗 2.7 倍额度)」，避免用户只看到额度掉得比预期快。

残留：

- **本机端到端未实测**。倍率行为目前只有 `WebApplicationFactory` 级的真实管线测试（真实注册、真实额度表、真实端点，上游打桩）。要在跑着的本地服务上复测需要一次有效登录：本次为修「重启即掉线」把 `Server:SigningKey` 固定了下来，代价是他之前用随机密钥签发的 token 全部失效，需重新登录一次；此后重启不再掉线。测量脚本留在 `publish/measure-plus-multiplier.ps1`（不进仓库），登录后跑它会打印 flash 与 plus 各自的额度增量（期望 100 与 270）。
- 全量测试里 `QwenMtImageTranslatorTests.CallerCancellation_MapsToCancelled` 与上一轮的 `Server.Tests` 各挂过一次，**单独跑均通过**，且 Providers 项目本次一行未改（`git diff` 为空）——判定为既有的时序不稳定用例，未修，另案处理。
- 图片与 OCR 链路不参与倍率：图片已有 `ImageQuotaChars=1000` 的固定折算，OCR 模型固定，两者都没有「同一段字符多种成本」的问题。
- 倍率是硬编码常量（与 `Pricing.Table` 同理：写错就是静默错账，不做成可调旋钮）。上游调价或换模型分词时，`Table` 与 `QuotaMultipliers` 要一起更新。

## v98 交互细节：注册/登录成功提示、未登录启动引导、语音浮层暂停/继续（2026-11-03）

用户反馈三条「UI 交互还是细节不够」：注册成功与登录成功全都没有提示；进去没登录态也不提示先登录；语音翻译浮层没有暂停/开始。另外把 ASR 最短计费从 10 秒降到 5 秒，并把 2,847 行的 `docs/IMPL.md` 拆册。

### 为什么这样改

- **提示条而不是模态框**：仓里原本三类反馈都不合适——`NoticeWindow` 是 `ShowDialog` 模态（AGENTS.md 记过：单 UI 线程上的模态对话框会冻结取词工具栏与结果卡）、托盘气泡被 Win11 通知设置吞掉（`App.xaml.cs` 的注释）、结果卡的 `ShowNotice` 私属于浮层。新增 `src/FastTranslation.App/ToastWindow.xaml(.cs)`：右下角、非模态、`ShowActivated=False`（不抢键盘焦点，用户正在输入的内容不被打断）、3 秒自隐（带按钮 6 秒，否则来不及点）、同一时刻只留一条。
- **注册/登录成功**：`AccountPage.Submit_Click` 成功后原本只有 `PasswordBox.Clear()` + 拉用量，面板从表单切到已登录卡片是唯一反馈，用户分不清「成功」还是「什么都没发生」。现在各补一条提示条。
- **未登录启动引导**：判定必须在 `TryRestoreAsync` **之后**（`App.RestoreAccountAsync`），因为本地 token 是后台恢复的，首屏永远是 XAML 里写死的「账号:未登录」——在那之前判未登录等于每次启动都瞎提示一次。Core 一路 `ConfigureAwait(false)`，续跑可能已不在 UI 线程，所以提示条用 `_ = Dispatcher.BeginInvoke(...)` 调度回去（`TreatWarningsAsErrors` 会把不 await 的 `DispatcherOperation` 报成 CS4014，`_ =` 是明写的 fire-and-forget）。首次运行（引导窗正在收集 API Key）不提示。
- **顺手修错位**：`ShowAccount()` 名字是账号、实际 `ShowPage(MainPageId.Plan)` 跳的是套餐页；托盘菜单项写的就是「账号」（`TrayIcon.cs:180`），结果卡那几处「先登录」引导也在叫用户去登录。落点改成 `MainPageId.Account`。
- **暂停 = 真的结束这条 WS 会话**（不是挂着连接不采集）。由服务端两条硬事实决定：① 会话是墙钟硬顶 `CancelAfter(sessionSeconds)`（`DashScopeSpeechGateway.cs:56`），空闲期照常计时，挂着不动白吃会话寿命（免费档一次会话只有 100 秒窗口）；② 收尾记账有两条路径，一条 usage 帧都没收到时按**整段墙钟**兜底（:180-185，v81 为堵「连上就砍」白嫖加的），开局就暂停、一句没说的那段会被全记到额度上——免费档最坏 100 秒 × 20 = 2,000 字符 = 当日全部额度。代价是每轮重开多付一次最短计费保底。
- **最短计费 10 秒 → 5 秒**：正是为了摊薄上面那个代价（200 → 100 字符，免费档日额度的 10% → 5%）。只说 1 秒仍记 100 字符 > 折算的 20 字符，保底依旧超记，没打开套利口子；真实成本另由 `Pricing.TextCostMicros` 与 `DailyBudgetMicros` 管。客户端 `App.xaml.cs` 抄了一份 `Math.Max(seconds, 10) * 20` 用来显示「已用 N 字符」，服务端降保底而这里不跟就会长期少记，所以两处裸数字收进 `SpeechQuotaGate.CharsPerSecond / MinBilledSeconds`，并由 `The_billed_minimum_is_five_seconds_of_speech` 钉住。
- **浮窗累计值不能掉回**：每暂停一次就是一条新会话，服务端 usage 从 0 重计。`SpeechWindow` 自己保 `_countedElapsed / _countedUsageChars`，`SetUsage` 显示「累计 + 本轮」，否则点「继续」后计时和「已用字符」会掉回小数字，用户以为额度没消耗。
- **浮窗只创建一次**：原来每条会话都 `??=` 复用窗口却重复 `+=` 事件，第二次会话起一次点击会收尾两次。暂停/继续必须复用同一个窗口，所以把订阅收进「新建时才订」的分支里。
- **暂停期间按热键 = 接着讲**：`RunSpeechTranslation` 原来只看 `_speechCoordinator`，暂停态下它是 null，再按热键会当全新会话把留着字幕的窗口清空。现在先看 `_speechWindow.IsPaused`。
- **IMPL 拆册**：单文件 2,847 行，读一次吃掉大量上下文。按每 20 个版本一册拆到 `docs/impl/`，`docs/IMPL.md` 变索引 + 写入规则；拆分用确定性脚本（`publish/split-impl.cjs`，不进仓库），拼回原文逐字节一致、小节集合 md5 一致，只差 4 处衔接空行。

### 补（同轮反馈）：首页「翻译」按钮过大、被输入框聚焦环压住

用户拿截图指出首页那颗「翻译」按钮太大且被输入框挤着。实拍核对后定位到三件事：

- **按钮档位跑偏**：`Padding="24,9"` 是全应用第二大的主按钮（只有文档页两个 26,10 比它大），而它处在一行里还要跟 `Ctrl/Enter` 键帽并排。降到 **20,6**，与语音页「开始语音翻译」同档。

### 补三：卡片的投影只打在轮廓上（用户选 A，全站机制改造）

用户反馈套餐页「进度条和阴影不符」。裁图 2 倍看清的现象是：用量环上的蓝点拖着一层糊影，6px 高的进度条却几乎没影子，两者看着不一致。

**根因**：`Card` / `CardSurface` 把 `CardShadowEffect` 挂在装着内容的 Border 上，而 WPF 的 `UIElement.Effect` 作用在元素**连同整棵子树**的渲染结果上——卡片里每样实体都各自落一层影子（浅色下 opacity 0.85 / blur 34 / depth 9，见 `ThemeBridge.cs:77`）。越实越饱和的元素越明显，细长的条就看不出来。

**单变量实验**：只给套餐 hero 那张卡加 `Effect="{x:Null}"`，重跑构建实拍——蓝点的糊影完全消失，文字也更干净。确认根因后才动手。

**做法**：新增 `src/FastTranslation.App/FtCard.cs`（`ContentControl` + 一个 `CornerRadius` 依赖属性），`App.xaml` 里加 `CardShell` 模板把两层拆开：一张**没有子元素**的底板负责投影，一张面负责内容、内边距与圆角裁切。`Card` / `CardSurface` 改成基于它的样式，26 处 `<Border Style="{StaticResource Card|CardSurface}">` 全部换成 `<local:FtCard>`（AccountPage 7、PlanPage 6、SettingsPage 4、DocumentPage 4、SpeechPage 3、MainPage 2）。

- 模板里投影写死 `DynamicResource CardShadowEffect` 而不是做成 `Shadow` 依赖属性：一是当时只有这一种影子，二是 `typeof(Effect)` 在 WPF 的 wpftmp 临时编译通道里编不过（CS0246）。主题切换仍跟着走，因为 DynamicResource 会重新解析。
- `CardShell` 必须显式设 `HorizontalContentAlignment` / `VerticalContentAlignment = Stretch`：Border 的子元素默认铺满，`ContentPresenter` 默认只占期望宽度，不写这两行套餐 hero 的 `1.12*/0.88*` 两列会缩成一团。

**事故与修复（必须记）**：批量改名脚本的下标算错——把开标签的替换点写成 `start + 7` 再删 7 个字符，结果 26 个开标签各被吃掉属性名的头 7 个字符（`<Border Style=` 变成 `<Borderlocal:FtCard"`）。闭标签算对了。修复没有靠猜：写 `publish/repair-cards.cjs` 拿参考版本（5 个文件用 `git show HEAD:`，PlanPage 用改动前的备份）逐行找「`<Border` 之后第 7 个字符起正好等于残段」的那一行，再按原样拼回 `<local:FtCard ...>`。SettingsPage 第一轮匹配不上，查明是它在工作区是 **CRLF** 而 HEAD 是 LF，比对时剥掉行尾 `\r`、写回时按原行补上才修好（没做整文件换行转换）。最后用归一化 diff 复核：把 `local:FtCard` 统一换回 `Border` 再与 HEAD 比，6 个文件除改名外只剩三处有意差异（MainPage 按钮、PlanPage 圆角、SettingsPage 上一轮的 `Plus(更高质量,消耗 2.7 倍额度)`），确认没丢东西。脚本的错误已就地改对。

验证：`dotnet build -c Release` 0 警告 0 错误；`dotnet test` 731 全绿；6 页实拍在 `publish/shots-v98/cards-audit/`（home / plan / settings / account / document / speech），影子仍在、糊影没了、布局没动。复习页与单词/短语/语句页不用这套样式，未受影响。为截图把只服务套餐页的 `FT_UITEST=plan` 分支换成通用的 `page-<枚举名>`。

残留与交底：

- **同类糊影还在这几处**：`TopPill`（顶栏药丸）、`PrimaryButton` 的 `bd`、`SidebarItem` 的 `fill` 也都是「容器带 Effect」，文字仍会各自投影（侧栏活动项下面那层糊影就是它）。用户批准的 A 说的是卡片，这三处没动；机制已经在了，要一起收掉随时可以做。
- **命名 gate**：`ToastWindow._current` 会被 `dotnet format --diagnostics IDE1006` 报一条「静态字段该用 Pascal」。`.editorconfig` 把这条记成已知误报（规则只按 `static` 分档，改成 `static readonly` 会把 243 处 `_camelCase` 误判），并写着「别照它改代码」，所以保留 `_current`。
- **`.editorconfig` 是未跟踪文件**（`git status` 里 `??`），而 AGENTS.md 的命名段指着它说「存量与已知误报见 `.editorconfig` 注释」——别人克隆仓库拿不到这份说明。要不要把它提交进去，等用户定。

### 补四：底板圆角绑定没生效（方形阴影），以及一处「未复现」

用户接着反馈两条：卡片圆角外面还有方形的影子；账号页「看套餐与价格」按钮被挡。

- **方形影子是我的机制里的真 bug**：底板那行写的是 `CornerRadius="{TemplateBinding CornerRadius}"`，同一个写法在面上生效、在底板上不生效（影子是方的、面是圆的）。没有继续猜原因，直接把两层的属性全部换成显式 `{Binding X, RelativeSource={RelativeSource TemplatedParent}}`，影子立刻跟着圆角走。同尺寸（2310 宽）修复前后各拍一张逐张比对确认。教训写进模板注释：这套两层结构不用 TemplateBinding。
- **账号页按钮：未复现，没有改**。在他原图上逐像素采样：按钮下边框在 y=466、卡片下缘在 y=500，中间 33px 是卡片白底，没有任何元素盖在它上面。又按他的窗口尺寸复现——他的截图是 1827 物理宽 ≈ **1040 逻辑宽，也就是默认窗口尺寸**，而我之前所有实拍都在 1320 逻辑宽的窗口上（那是我之前调布局留下的状态），等于一直在错的尺寸下验收。给 `main-shot.ps1` 加了 `-Width/-Height`（Win32 `MoveWindow`）后按 1820×1295 重拍账号页，间距同样是 33px。所以这条请他指认到底看到什么。

### 补五：补三/补四那套「底板+面」机制已整体回退

用户接着反馈两条：圆角卡片普遍在左侧上下角有方形阴影；套餐消耗度的颜色与阴影对不上。

第一条是补三那套机制自己引入的。放大 6 倍看角落：影子是硬边的方形楔块，不跟圆角走。实验顺序与结果：

1. 底板写 `{TemplateBinding CornerRadius}` → 楔块在；换成 `{Binding ..., RelativeSource={RelativeSource TemplatedParent}}` → 楔块仍在；圆角写成字面量 `16` → **一模一样**。所以不是绑定问题。
2. 把底板涂红再拍：红色沿卡片**四条边和四个角**都露出一圈，说明底板比面大了一线，它的影子在角上就形成那块楔块。
3. 与改造前同坐标对比（`cmpA-before-focard.png` 是单 Border 带 Effect 的版本）：改造前角落干净，没有这圈残影。

结论：这套拆层没有达到目的，反而更糟，**整体回退**——`FtCard.cs` 删除，`CardShell` 模板删除，`Card` / `CardSurface` 恢复成带 `Effect` 的 Border 样式，26 处用法换回 `<Border>`（纯文本替换即可，标签名唯一）。回退后同坐标复拍 `revert-corner.png`，角落与改造前一致。构建 0 警告 0 错误，`dotnet test` 731 全绿。

这条弯路本身记进 `App.xaml` 的样式注释：**不要再走「把 Effect 拆到无子元素的底板」这条路**，实测会在卡片边缘留一圈残影。

第二条（消耗度的颜色与阴影对不上）随回退回到原状：用量环 12px 粗的圆头弧在卡片投影下拖出糊影，6px 的进度条几乎看不出，两者观感不一致。这是容器 Effect 的固有行为，拆层已被证明不可行，剩下的选择是**改观感而不是改机制**（环与条只留一种表达，或把条加粗到与环同权重），需要用户定方向后再动。

本轮另外两条已落地：套餐 hero 右侧面板的 `CornerRadius="0,16,16,0"`（补三之前那条），首页「翻译」按钮 `20,6 → 18,5`。

## v99 卡片残影与用量环：摘掉切投影的矩形裁剪，弧半径回到环中线（2026-11-04）

用户反馈两条：套餐页与首页卡片左侧圆角有三角残影；用量环的彩色圆点没和灰环对齐，很突兀。

### 为什么这样改

- **残影根因**：`CardSurface` 与套餐页 hero 卡把 `Effect` 和 `ClipToBounds` 放在同一个 Border 上。WPF 的矩形裁剪发生在 Effect **之后**：投影伸出盒外的部分被整圈切掉，只剩矩形内、圆角轮廓外那一块（圆角与方角之间）→ 四个三角残影，盒外应有的柔和投影反而没有。修法是摘掉裁剪：hero 右侧渐变面板 v98 起已自己收 `0,16,16,0` 圆角，首页译文竖线有 16 内边距不贴边，现状没有任何内容依赖这层矩形裁剪。将来若加贴边色块，要自己收圆角或另包一层带 `ClipToBounds` 的内 Border——裁剪与投影不能同一个 Border 兼，这条写进了 `App.xaml` 的样式注释。
- **不走底板路**：v98 末实测过「把 Effect 拆到无子元素的底板」会留一圈残影并已回退（见 v98 末探针），本次只摘裁剪、不拆层。
- **圆点根因**：`Ellipse` 的描边画在元素盒内侧（几何 = 盒 − 描边），106 盒的环中线半径是 (106−12)/2 = 47；`UpdateRing` 的弧按半径 53 画，圆头正好骑在灰环外沿上。截图实测圆点中心偏离环中线约 10px（≈6 UI px，恰为半个描边宽）。`RingRadius` 改 47，与灰环共用中线。

### 验证

- `dotnet build FastTranslation.slnx -c Release` → 0 警告 0 错误；`dotnet test` → 310/107/95/219 = **731 全绿**。
- 截图（`tools/qa/shot-v99-cards.ps1` 新增，产物 `assets/qa/v99-main.png` / `v99-plan.png`）：两页卡片四角均无三角残影，投影恢复为圆角矩形外一圈柔和投影；用量环圆点落在环带上。
- 像素复核（`v99-plan.png`，窗口缩放 1.75）：灰环带厚 23px、中线半径 82px ≈ 47 UI；圆点 bbox y 474..494 与环顶带位置完全重合（该带被圆点盖住），圆点中心与环中线偏差 0px（改前约 10px）。
- 应用重启交付：Release 产物进程存活，主窗口标题 `Fast Translation`。

### 残留风险

- 摘掉 `ClipToBounds` 后，将来若新增贴卡片边的色块且不收圆角，会顶出圆角外（约束已写进 `App.xaml` 注释）。
- 用量环的弧与卡内其它内容一样带 `CardShadowEffect` 的柔和投影，这是容器投影的固有观感（v98 末讨论过），本次只修对齐、不改观感。
