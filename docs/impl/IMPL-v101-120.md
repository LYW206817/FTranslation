## v101 复习队列：未学新卡不再随日期消失，日配额改按首次评分计数

### 为什么

设计稿把新卡配额定义成 `COUNT(stage = 0 AND created_at >= dayStart)`，实现又把同一个条件用在了 `ListFresh` 上。于是「今天创建的卡」被当成了「今天要学的卡」：用户某天存了 30 张、只学完 20 张，第二天起剩下的 10 张既不进 `due`（`stage` 还是 0），也不进 `fresh`（`created_at` 早于新一天的零点），**永久从复习队列里消失**。设计稿里「没有队列表、计数自动收敛」的前提，建立在「未学的新卡一直留在 stage 0」上；过滤掉旧卡正好把这个前提破坏了。

第二个问题是日界线：客户端用 `utcNow - utcNow % 86400` 算 `dayStart`，而设计明确要求「客户端送自己的本地零点」。UTC+8 用户的新卡配额实际在本地 08:00 才重置，00:00–08:00 之间存的卡还会在 08:00 后从队列里消失。

### 改了什么

**服务端**

- `Storage/ServerDatabase.cs`：`notes` 新增 `first_reviewed_at INTEGER NOT NULL DEFAULT 0`（建表与 `EnsureColumn` 两处）。迁移时对 `stage >= 1 AND first_reviewed_at = 0` 的旧行用 `reviewed_at` 回填——不回填的话，老卡下一次复习会被当成「今天首学」，白吃当天配额。索引 `ix_notes_user_first_reviewed` 把日配额查询限制在当天的行上。
- `Storage/NoteStore.cs`：
  - `ListFresh(Guid, int)` 去掉 `created_at >= dayStart`，返回所有 `stage = 0` 的卡（`created_at ASC`），只按调用方给的条数截断；返回值从 `(Items, Total)` 收成 `IReadOnlyList`，`Total` 原本没人用。
  - `CountFreshSince` 改成 `CountIntroducedSince`：`COUNT(stage >= 1 AND first_reviewed_at >= dayStart)`。同一张卡当天复习多次只算一张，因为 `first_reviewed_at` 只在从 0 变一次。
  - `SetReview` 写入时 `first_reviewed_at = CASE WHEN first_reviewed_at = 0 THEN $reviewedAt ELSE first_reviewed_at END`。
- `Api/NotesEndpoints.cs`：`quota = max(0, newLimit - introduced)`；`fresh` 只在 `quota > 0` 时取，并按 `quota` 截断。没学完的卡不会消耗配额，下一次请求会继续出现。

**客户端**

- `Core/Notes/ReviewSchedule.cs` 新增 `StartOfLocalDay(DateTimeOffset now)`：按调用方偏移取本地零点。
- `Pages/ReviewPage.xaml.cs` 与 `MainWindow.xaml.cs` 的复习角标都改用它，不再用 UTC 零点。

### 验证

- `dotnet build FastTranslation.slnx -c Release` → **0 警告 0 错误**。
- `dotnet test` → Core 312 / Platform.Windows 107 / Providers.QwenMt 95 / Server 224 = **738 全绿**。
- 新增/改写的用例：
  - `Store_ListFreshKeepsCardsFromEarlierDays`：创建后把时钟拨快 3 天，卡仍在 fresh；同一测试里用旧谓词 `created_at >= 当日零点` 直接查库断言结果为 0，把「修的是什么」钉住。
  - `Store_CountIntroducedSinceUsesTheFirstReview`：同一张卡当天复习两次，`dayStart` 卡在两次之间时仍只算 1；`dayStart` 在两次之后算 0。
  - `Review_UngradedFreshCardsSurviveIntoTheNextDay`：今天用掉 1 个名额、队列为空；把 `dayStart` 推到明天后，昨天没学的卡回来且配额重置。
  - `Review_QuotaCountsFirstReviewOnly`：同一张卡点两次「忘记」只占 1 个新卡名额。
  - `Review_FreshQuotaShrinksWhenMoreCardsThanTheLimitExist`：按新语义改写（未评分时配额是满的，评分后才减）。
  - `Migration_BackfillsFirstReviewedAtForExistingGradedCards`：把已评分行的 `first_reviewed_at` 清零后重跑 `Initialize()`，回填成 `reviewed_at`。
  - `Migration_OldDatabaseGainsTheReviewColumns`：补 `first_reviewed_at` 列存在断言。
  - Core：`StartOfLocalDay_UsesTheCallersOffset`（UTC+8 与 UTC 零点差 16 小时）、`StartOfLocalDay_HandlesNegativeOffsets`（UTC-5）。
- **测试有效性**：`Store_ListFreshKeepsCardsFromEarlierDays` 里的旧谓词断言在修复前为 1、修复后为 0；若把 `ListFresh` 的 `created_at` 过滤加回去，该用例会失败。没有单独做「改坏再跑」的反证。

### 残留风险

- 迁移回填用 `reviewed_at`（最后一次评分）而不是真正的首次评分时间。升级后第一次启动时，某张「很久以前首学、今天又复习过」的卡会被算进当天配额；只影响升级当天，之后 `first_reviewed_at` 不再变化。
- `StartOfLocalDay` 用当前偏移算当天零点。有夏令时的时区在切换当天可能差一小时；目标用户在中国（无夏令时），暂不处理。
- 日配额按「首次评分」计：用户把卡拉进界面但没评分，不消耗名额，下次还会出现。这是刻意的，否则「看一眼就算学过」。
- 客户端仍写死每次请求 20 张新卡，尚未进设置页；这是既有设计。
- 没有跑真实账号的端到端联调：服务端用 `WebApplicationFactory` 级测试覆盖了队列与迁移，客户端日界线用纯函数单测覆盖；界面层没有改动。

## v102 账号设备管理：可查看、可移除，设备上限不再是死路

### 为什么

服务端从 v45 起就有每账号 3 台设备的上限，但只实现了「登录时登记」。账号页看不到设备，也没有移除入口；第 4 台设备登录只会拿到 `{"error":"device_limit_reached"}`，而客户端 `MapFailure` 没有这个分支，最终显示成通用的「账号服务器出错了」。用户没有任何自助出路。

第二个问题是移除的语义。refresh token 原本只记 `user_id`，不记设备；即使补一个删除接口，删完设备行后旧设备仍能用 refresh token 续期，下一次网关调用又会把名额占回来——「移除」只是把列表项删掉而已。

### 改了什么

**服务端**

- `Storage/ServerDatabase.cs`：`refresh_tokens` 新增 `device_id TEXT`（建表 + `EnsureColumn`，旧行 NULL）。`ON DELETE CASCADE` 在这里不可依赖：`PRAGMA foreign_keys` 是连接级开关，而每次操作都开新连接，所以 `DeleteDevice` 显式删子行。
- `Storage/AccountStore.cs`：
  - `ListDevices(userId)`：按 `last_seen_at DESC, created_at DESC` 返回该账号的设备。
  - `DeleteDevice(userId, deviceId)`：事务内先校验设备归属，再吊销该设备的 refresh token、删 `usage_daily`、删设备行。先校验归属是必要的——否则传别人的 `deviceId` 可以抹掉对方的日用量，即使最后的删除返回 0。
  - `SaveRefreshToken` 增加可选 `deviceId`；`ConsumeRefreshToken` 返回 `RefreshTokenOwner(UserId, DeviceId)`，轮换时把设备带下去。旧令牌 `DeviceId = null`，不受影响。
- `Api/AuthEndpoints.cs`：登录/改密签发时把设备 id 写进 refresh token；刷新时沿用原设备。
- `Api/AccountEndpoints.cs`：
  - `GET /api/v1/account/devices`：用 `X-FT-Device` 指纹标出 `isCurrent`，并下发 `maxDevices`（客户端不写死 3）。
  - `DELETE /api/v1/account/devices/{id}`：不存在或不属于本账号返回 404 `device_missing`（不向别的账号确认 id 存在）；指纹与目标一致返回 400 `device_is_current`。
- `Api/Contracts.cs`：`DeviceDto` 增加 `IsCurrent`；新增 `DeviceListResponse(Devices, MaxDevices)`。

**客户端**

- `Core/Account/AccountTypes.cs`：`AccountDevice`（当前设备固定显示「这台电脑」，指纹不下发）、`AccountDeviceList`、`DescribeLastSeen`；错误码新增 `DeviceLimit` / `DeviceIsCurrent` / `DeviceMissing`，`device_limit_reached` 的文案明确指向「在已登录设备上移除一台；旧设备都不在了请联系我们」。
- `Core/Account/AccountApiClient.cs`：`GetDevicesAsync` / `RemoveDeviceAsync`，指纹走 `X-FT-Device` 头；`MapFailure` 补三个设备错误码。
- `App/AccountCoordinator.cs`：`ReadDevicesAsync` / `RemoveDeviceAsync`，走现有的 `WithSessionAsync`（access token 过期会自动刷新重试）。
- `Pages/AccountPage.xaml(.cs)`：账号页新增「登录设备」卡片，显示「已登记 n / 上限 台」、当前设备徽标与「上次登录」相对时间；非当前设备有「移除」按钮，点击先走 `NoticeWindow.Confirm`。退出登录时清空列表，避免上一个账号的设备名闪一帧。
- 当前设备不显示机器名，统一显示「这台电脑」；日常使用与截图都不会把机器名带出去。

### 残留风险

- 移除设备只吊销 refresh token；已经签发的 access token 在过期前（最长 30 分钟）仍然有效。这段窗口内旧设备仍能调用账号接口，也可能在有空位时通过网关重新登记设备。要彻底封死需要给 access token 加设备校验或加设备墓碑，本次不做。
- v102 之前签发的 refresh token `device_id` 为 NULL，移除设备不会吊销它们；它们最多再活 90 天，改密码会一次性清掉。
- 删设备会清掉该设备的 `usage_daily`（设备级「今日」用量），但保留 `usage_events` 审计行；月度用量不受影响。这是刻意的。
- `DELETE` 的「当前设备」保护依赖 `X-FT-Device` 头；直接调接口且不送头的调用方可以删掉自己正在用的设备。这是自伤而非越权，未加额外限制。
- 设备列表只在进入账号页或点「刷新」时更新，不是实时推送。
- 没有做移除设备的邮件确认；同一账号的任意已登录设备都能移除其他设备。
- 没有跑安装包升级后的数据库迁移；迁移只在本地开发库与测试临时库上验证过。

## v104 单英文词显示本地词典卡（ECDICT）

### 为什么

`qwen-mt-flash/plus` 是专用机器翻译模型：`messages` 只允许一条 user 消息，
`translation_options` 只控制语种、术语与领域，输出是纯译文。划词查一个词只能得到
「银行」这类单一意思，没有音标、词性、多义项，和词典类工具差一截。这不是提示词能修的。

2026-11-06 在本机用真实 Key 做了 10 词对比（未提交探针）：

- `qwen-flash` + JSON 输出：JSON 合法 10/10，音标 10/10，但全量耗时 **1.95–4.26 s**（中位约 3.2 s）；
  多义词会编造义项——`bank` 生成「体育运动中的得分区」「椅子的靠背」，例句
  `He leaned against the bank of the chair.` 不是英语。
- `qwen-mt-flash` 基线：单词语句 **250–400 ms**。
- ECDICT 裁剪子集：**57,841 词 / 5.3 MB**，查询 **0.35 ms**，测试 10 词全部命中。

结论：单词卡必须本地优先；通用模型只适合做词库未命中的兜底与例句生成（本版未接）。

### 改了什么

- `tools/dictionary/build-ecdict.py`：从 ECDICT（MIT）CSV 生成只读词库 `assets/dictionary/ecdict.ftd`（FTD1）。
  只保留考试标签词与 `frq`/`bnc` > 0 的词条；词头、音标、释义、词形、标签按 tab 分隔，
  索引在文件头；不做全量 77 万词，避免安装包膨胀。
- `Core/Lexicon/`：
  - `DictionaryTypes.cs`：`DictionaryEntry` / `DictionarySense` / `ILexicon`；
  - `WordShape.cs`：只有「单个英文词」才查词，剥掉首尾标点，保留词内 `-` 与 `'`；
  - `EcdictText.cs`：把 ECDICT 的 `n. / vt. / vi. / a.` 归一成 `n. / v. / adj.`，同词性合并，
    无词性行挂到上一个义项；解析词形（跳过 `0:`/`1:` 原形）与考试标签；音标补斜杠并把 `ә`/`ǝ` 换成 `ə`；
  - `EcdictLexicon.cs`：启动时读索引进内存，查询时按偏移读一条；文件缺失/损坏返回 null，在线翻译不受影响。
- `Core/TranslationService.cs`：缓存未命中后，若「英→中 + 单英文词 + 词库命中」，直接返回 `Dictionary`
  结果（`Model = "ECDICT"`，耗时约 0 ms），不进 provider、不建 in-flight CTS；结果照常进 LRU。
- `Core/TranslationTypes.cs`：`TranslationResult.Dictionary` 可空字段。
- `Platform.Windows/OverlayWindows.cs`：结果卡新增词典块——音标、词性徽标 + 释义（最多 4 组、每组 6 条）、
  词形与考试标签；词典块与译文行互斥显示，加载/错误/提示态都会收起词典块。
- `App/App.xaml.cs`：启动时从 `AppContext.BaseDirectory/dictionary/ecdict.ftd` 加载；缺失只写一条 Trace。
  新增 `FT_UITEST=wordcard` 截图入口，走真实 `TranslateAsync`（不是手搓结果）。
- `FastTranslation.App.csproj`：词库按 Content 复制到输出目录；安装器本来就整目录打包，无需改 `.iss`。

- `dotnet test` → Core 347 / Platform.Windows 107 / Providers.QwenMt 95 / Server 233 = **782 全绿**

## v105 单词本保存词典快照

### 为什么

v104 的词典卡只在结果卡上停留：点「保存」进单词本后只剩原文与译文两行，复习时看不到
音标、词性、义项，词典卡最有价值的部分恰好丢了。保存应当保存用户看到的那张卡。

### 改了什么

- 服务端：
  - `notes` 表新增 `dictionary_json TEXT NOT NULL DEFAULT ''`（建表语句 + `EnsureColumn` 迁移）。
  - `SaveNoteRequest.Dictionary`（`JsonElement?`）只透传不解析，服务端不需要理解词性结构；
    上限 8 KB，超限只丢词典、词条照常保存。`NoteDto.Dictionary` 原样返回。
  - 重复保存（同类型 + 同原文）时，若老行没有词典快照而这次带了，补写一次；
    不改 `updated_at`——用户看不出这是一次写操作。
  - `NoteStore.Create` / `ReadNote` / `SetDictionary` 与 5 处 SELECT 同步加列。
- Core：
  - `Note.Dictionary`；`NotesApiClient` 的 `SaveBody` 与 `NoteResponse` 映射；
  - `DictionaryEntry.ToDisplayText()`：音标 + 按词性分行 + 词形 + 考试标签，
    与结果卡一样最多 4 组、每组 6 条，供单词本详情与复习页共用。
- 客户端：
  - 结果卡保存、首页保存把 `result.Dictionary` 传给 `AccountCoordinator.SaveNoteAsync`；
  - 单词本详情新增「词典」段；复习页答案下方新增同样一段；没有词典的老词条整段隐藏。
- QA：`FT_UITEST=notes-demo` 喂一条演示词条，不登录、不联网；README 增加单词本截图。

### 验证

- `dotnet build FastTranslation.slnx -c Release` → **0 警告 0 错误**。
- `dotnet test` → Core 349 / Platform.Windows 107 / Providers.QwenMt 95 / Server 236 = **787 全绿**
  （v104 为 782，本次 +5）。
- 新增用例：
  - 服务端：保存带词典 → 响应与列表都带回来；超过 8 KB 只丢词典；老词条重新保存补齐词典且 Id 不变。
  - 客户端：`SaveAsync` 请求体包含 `dictionary`/`partOfSpeech`，响应能反序列化成 `DictionaryEntry`。
  - Core：`ToDisplayText` 包含音标、词性释义、词形与标签。
- 界面截图：`assets/screenshots/wordbook-dictionary.png`（单词本详情「词典」段，取样位置：
  charge 条目的音标、n./v. 义项、变形与词表）。原始整窗截图里有本机账号，只留在
  `assets/qa/`（gitignore），提交的是裁掉左下角账号栏的版本。
- 服务端迁移：`EnsureColumn` 会在下次启动时给本地库补列；未在真实生产库上执行。

### 残留风险

- 词典是保存那一刻的快照，之后换词库不会回填；已有词典的词条再次保存也不会更新（只在为空时补齐）。
- 8 KB 上限对当前单词语料足够；如果以后把例句也存进来，需要重新评估。
- 复习页只改了文本块，没有单独截图；它与单词本详情共用 `ToDisplayText()`，但没有视觉证据。
- 真实保存链路的 E2E（登录账号 → 点保存 → 重新登录看到词典）没有跑；服务端与客户端两端分别有测试，
  UI 截图走的是演示数据入口。
