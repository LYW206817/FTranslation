## v101 复习队列：未学新卡不再随日期消失，日配额改按首次评分计数

### 为什么

设计稿把新卡配额定义成 `COUNT(stage = 0 AND created_at >= dayStart)`，实现又把同一个条件用在了 `ListFresh` 上。于是「今天创建的卡」被当成了「今天要学的卡」：用户某天存了 30 张、只学完 20 张，第二天起剩下的 10 张既不进 `due`（`stage` 还是 0），也不进 `fresh`（`created_at` 早于新一天的零点），**永久从复习队列里消失**。设计稿里「没有队列表、计数自动收敛」的前提，建立在「未学的新卡一直留在 stage 0」上；过滤掉旧卡正好把这个前提破坏了。

第二个问题是日界线：客户端用 `utcNow - utcNow % 86400` 算 `dayStart`，而设计明确要求「客户端送自己的本地零点」。UTC+8 用户的新卡配额实际在本地 08:00 才重置，00:00–08:00 之间存的卡还会在 08:00 后从队列里消失。

### 改了什么

**服务端**

- `Storage/ServerDatabase.cs`：`notes` 新增 `first_reviewed_at INTEGER NOT NULL DEFAULT 0`（建表与 `EnsureColumn` 两处）。迁移时对 `stage >= 1 AND first_reviewed_at = 0` 的旧行用 `reviewed_at` 回填——不回填的话，老卡下一次复习会被当成「今天首学」，白吃当天配额。索引 `ix_notes_user_first_reviewed` 把日配额查询限制在当天的行上。
- `Storage/NoteStore.cs`：
  - `ListFresh(Guid, int)` 去掉 `created_at >= dayStart`，返回所有 `stage = 0` 的卡（`created_at ASC`），只按调用方给的条数截断；返回值从 `(Items, Total)` 收成 `IReadOnlyList`，`Total` 原本没人用。
  - `CountFreshSince` 改成 `CountIntroducedSince`：`COUNT(stage >= 1 AND first_reviewed_at >= dayStart)`。同一张卡当天复习多次只算一张，因为 `first_reviewed_at` 只在从 0 变一次。
  - `SetReview` 写入时 `first_reviewed_at = CASE WHEN first_reviewed_at = 0 THEN $reviewedAt ELSE first_reviewed_at END`。
- `Api/NotesEndpoints.cs`：`quota = max(0, newLimit - introduced)`；`fresh` 只在 `quota > 0` 时取，并按 `quota` 截断。没学完的卡不会消耗配额，下一次请求会继续出现。

**客户端**

- `Core/Notes/ReviewSchedule.cs` 新增 `StartOfLocalDay(DateTimeOffset now)`：按调用方偏移取本地零点。
- `Pages/ReviewPage.xaml.cs` 与 `MainWindow.xaml.cs` 的复习角标都改用它，不再用 UTC 零点。

### 验证

- `dotnet build FastTranslation.slnx -c Release` → **0 警告 0 错误**。
- `dotnet test` → Core 312 / Platform.Windows 107 / Providers.QwenMt 95 / Server 224 = **738 全绿**。
- 新增/改写的用例：
  - `Store_ListFreshKeepsCardsFromEarlierDays`：创建后把时钟拨快 3 天，卡仍在 fresh；同一测试里用旧谓词 `created_at >= 当日零点` 直接查库断言结果为 0，把「修的是什么」钉住。
  - `Store_CountIntroducedSinceUsesTheFirstReview`：同一张卡当天复习两次，`dayStart` 卡在两次之间时仍只算 1；`dayStart` 在两次之后算 0。
  - `Review_UngradedFreshCardsSurviveIntoTheNextDay`：今天用掉 1 个名额、队列为空；把 `dayStart` 推到明天后，昨天没学的卡回来且配额重置。
  - `Review_QuotaCountsFirstReviewOnly`：同一张卡点两次「忘记」只占 1 个新卡名额。
  - `Review_FreshQuotaShrinksWhenMoreCardsThanTheLimitExist`：按新语义改写（未评分时配额是满的，评分后才减）。
  - `Migration_BackfillsFirstReviewedAtForExistingGradedCards`：把已评分行的 `first_reviewed_at` 清零后重跑 `Initialize()`，回填成 `reviewed_at`。
  - `Migration_OldDatabaseGainsTheReviewColumns`：补 `first_reviewed_at` 列存在断言。
  - Core：`StartOfLocalDay_UsesTheCallersOffset`（UTC+8 与 UTC 零点差 16 小时）、`StartOfLocalDay_HandlesNegativeOffsets`（UTC-5）。
- **测试有效性**：`Store_ListFreshKeepsCardsFromEarlierDays` 里的旧谓词断言在修复前为 1、修复后为 0；若把 `ListFresh` 的 `created_at` 过滤加回去，该用例会失败。没有单独做「改坏再跑」的反证。

### 残留风险

- 迁移回填用 `reviewed_at`（最后一次评分）而不是真正的首次评分时间。升级后第一次启动时，某张「很久以前首学、今天又复习过」的卡会被算进当天配额；只影响升级当天，之后 `first_reviewed_at` 不再变化。
- `StartOfLocalDay` 用当前偏移算当天零点。有夏令时的时区在切换当天可能差一小时；目标用户在中国（无夏令时），暂不处理。
- 日配额按「首次评分」计：用户把卡拉进界面但没评分，不消耗名额，下次还会出现。这是刻意的，否则「看一眼就算学过」。
- 客户端仍写死每次请求 20 张新卡，尚未进设置页；这是既有设计。
- 没有跑真实账号的端到端联调：服务端用 `WebApplicationFactory` 级测试覆盖了队列与迁移，客户端日界线用纯函数单测覆盖；界面层没有改动。
